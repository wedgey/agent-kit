# An epic runs one lane per ticket

Conductor first ran every task from one session. The orchestrator spawned implementers, reviewers and verifiers as delegates and owned every verdict. That holds for one feature, but an epic of several PRs breaks it. Every brief and report lands in one context, which fills across tickets. A role delegate cannot ask anything and stops BLOCKED, so it cannot be steered mid-ticket. And an implementer cannot spawn its own reviewer, so one ticket cannot run a whole playbook. So conductor sizes the work itself, with or without an epic issue, and runs work that needs two or more PRs as an epic. The orchestrator cuts it into tickets, draws their graph and dispatches each ready ticket to a lane. A lane is a background delegate in its own worktree that runs the feature, bug-fix or refactoring playbook as its own orchestrator, writes the ticket's code itself, carries its PR to merge-ready and reports at fixed points. It runs at strong-code, because its ticket arrives specified and its reviewer and verifier still run at frontier, and at frontier when the ticket needs design or the lane escalates. The orchestrator writes no ticket's code, keeps the graph and the lanes' reports, verifies the combined result, and lands through shipping only on request. Working lanes stay within the queue's slots, because a lane parked on a full queue does nothing (ADR 0007). Two probes on Claude Code v2.1.309 showed a worktree-isolated background subagent can spawn its own delegates, take messages while idle, wake on its own background work after minutes, and pass through a repo's heavy-command hook. So the Claude Code binding makes a lane a subagent, which groups it under its ticket and shares the orchestrator's permission mode, and keeps a separate `claude --bg` session as the fallback when an epic must outlive the orchestrator.
