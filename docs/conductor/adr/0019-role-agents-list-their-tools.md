# Role agents list their tools

Every tool and skill a delegate can see is sent again on each of its turns. On 2026-11-21 a haiku delegate in a large repo started at 36.0k input tokens with the role agents' deny lists, which removed only `Agent` and the edit tools. About 11k of that was the `Skill` tool's skill listing, and much of the rest was tools the role never calls. Past transcripts showed which tools each role used: Bash and Read above all, then Monitor, Edit, Write, SubagentHandback, TaskStop, SendMessage and ToolSearch, and `Skill` mostly from lanes, implementers and verifiers.

So each conductor role agent names its tools with a `tools:` allowlist, as design-process did in its ADR 0003. `ToolSearch` is on every list, which keeps rare tools such as `Monitor`, `WebFetch` and `SendMessage` deferred until called. `Skill` stays only on the lane, implementer and verifier; the explorer, reviewer and editor read a `SKILL.md` the brief points to. Measured the same way, a reviewer or explorer starts at 16.8k, a verifier at 27.7k and a lane at 31.4k.

A list can name a whole MCP server but has no wildcard, and a published plugin cannot name the servers each repo uses. So role agents get no MCP tools. A brief that needs MCP data goes to the fallback agent type or carries the data in CONTEXT, and a lane checks deploys with `gh` or the provider's CLI. Past use was small: 16 analytics calls by explorers, 6 by verifiers, 4 by reviewers and 5 deployment calls by lanes, across about 900 delegate runs. This amends ADR 0006, whose role agents carried the tools a role may not use.
