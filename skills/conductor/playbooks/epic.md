### Epic

**You own the ticket graph and the epic's verdict.** Lanes own their tickets, through to the merge. You decide what runs, in what order, and when the epic is done. You run no checks and no merges yourself, because every turn of yours re-reads the whole epic.

Several tickets toward one outcome, each ending in its own PR. You dispatch one lane per ticket and steer them. You write no ticket's code. A single ticket is not an epic, so run its own playbook.

1. **Pin the tickets.** The tracker holds the epic and one issue per ticket. When the operator gave you a body of work rather than tickets, cut it into tickets and create the issues yourself. With no tracker, write the tickets to one file outside the repo's tree and paste each ticket in full into its lane brief. Each ticket must stand alone: the outcome, the files it owns, what is out of scope, and acceptance that ends in an end-to-end check. Fill the gaps yourself from the code. Product and preference calls go to the operator through ask, batched into one round. Settle in the ticket each design point the code can answer, such as where a boundary sits, what a key holds or which reads a change covers. A new data shape or a crossed module boundary is a point to settle, not a flag by itself. Flag a ticket **needs design** only when a point depends on what the lane will find, such as a cut chosen from a measurement, or when you could not make its acceptance concrete. Its lane runs at frontier. Every other lane runs at strong-code, because its ticket arrives specified and its reviewer and verifier still run at frontier.
2. **Draw the graph.** For each ticket, list the files it writes and the tickets it needs. show it as a Mermaid diagram. Tickets that others need, such as a schema change, a migration, shared types or a flag, are the backbone. Two tickets whose write lists overlap get split or chained, per [separate-before-sharing](../principles/separate-before-sharing.md). Record the graph on the epic's issue, or in the tickets file.
3. **Size the lanes.** Every lane runs heavy checks through the box queue, so working lanes beyond its slots sit parked. Count the slots of the queue your lanes lean on most, per [queue-heavy-checks](../principles/queue-heavy-checks.md), and keep no more lanes working at once than that. A lane whose PR is merge-ready and waiting to land is not working. Say the number and why.
4. **Dispatch the ready tickets.** Find the repo's documented command that prepares a fresh worktree once, and put it in every brief's SETUP. A ticket is ready when every ticket it needs has merged. It is also ready when all but one have merged and that one has a merge-ready PR, and then its lane stacks on that PR's branch. A ticket waiting on two unmerged tickets waits for the merges. When ready work waits only on merges, ask the operator once to land those PRs. dispatch one lane per ready ticket, up to the size from step 3, each with a lane brief from roles.md. track each ticket as its own item, led by its number, and update it from the lanes' reports. Start a lane watch for each lane in the background, as the binding says, because a lane that stalls mid-turn sends no report.
5. **Steer by notices.** Each lane reports back when it is merge-ready, its head moved, it is blocked or it failed. wait for those reports and never poll. A notice that needs nothing from the operator gets no reply text: update the ticket's item and end the turn. Write to the operator only when a ticket lands or fails, a lane needs a product call, or the operator asked. When a notice arrives:
   - **Merge-ready.** Read the reviewer's STATUS and the verifier's verdict on the PR, and the diff's file list and size. A lane saying "ready" is a claim. spawn a reviewer only when the files or the size surprise you. A lane under LAND waits for your go before it merges, so send go, through continue, once this check passes. Then dispatch the next ready ticket.
   - **Context full.** dispatch the same brief at the same tier, with BRANCH set to the pushed branch and the report pasted in full under CONTEXT. stop the old lane. This is a handover, not an escalation.
   - **Head moved.** Lanes stacked on that branch see it through their own watcher and rebase themselves. Message a stacked lane only when it is not watching, such as a lane you just resumed.
   - **Merged.** Close the lane per step 8, then dispatch the next ready ticket. A lane that landed under LAND reports its own post-merge check, so you run none.
   - **Escalate.** A Failed report, or a Blocked report on a design question from a lane at strong-code, goes one tier up, per roles.md Escalation. have the lane push its branch, stop it, and dispatch the same brief at frontier with BRANCH set to that branch and the failure attached. A failure at frontier comes back to you.
   - **Blocked.** Any other block gets a reply. Settle what you can. Product calls go to the operator through ask. A second block on the same premise means [attack-the-premise](../principles/attack-the-premise.md) before anything else.
   - **A change others build on.** When one lane changes an interface another lane uses, tell that lane what changed and where.
   - **Stalled.** The lane watch reports a lane quiet in the middle of a turn. Read the lane's state, as the binding says, then continue it with what it was doing and what its worktree holds, and start its watch again. A second stall in the same stage means stop it and dispatch the same brief with BRANCH set to its pushed branch, as for Context full. stop a lane only to replace it, and say why on its ticket.
6. **Verify the epic.** When the operator asked to land each ticket as it passes, run this once on trunk after the last merge, and spawn the verifier there. It can no longer stop a merge, so a failure becomes a new ticket. Otherwise, when every ticket's PR is merge-ready, build the combined result in a scratch worktree, the top of the stack or every branch merged in graph order, yourself or through an editor, and run SETUP there. Then spawn one verifier on that worktree against the epic's own acceptance. One ticket can pass alone while the epic still fails, so this check is never skipped.
7. **Land on request.** Only an explicit request to land, ship or merge lets a ticket land. Pass it to each lane it covers as LAND, quoted, through continue, and to later lanes in their brief. Each lane lands its own PR per roles.md "Lanes", in graph order because a stacked lane lands only once its base has merged and it has rebased onto trunk. Each lane owns its own rebase. A request such as "merge them as soon as they pass" covers every lane until the operator withdraws it. Pass a withdrawal to each lane as `LAND no`.
8. **Close the lanes.** When a ticket's PR has merged, stop its lane and its watch, remove its worktree and tick its item. Update the epic's issue, or the tickets file, with what landed, what did not, and why.

9. **Hand over the epic.** When the binding tells you that your context passed the limit, finish the notice in hand and start nothing new. A fresh orchestrator steers from a small context, and this one re-reads a large one on every notice.
   - Ask every working lane to push its branch and report Context full, through continue, and wait for those reports.
   - Write the epic's state to its issue, or the tickets file: one row per ticket with its lane, branch, PR and status, each lane's Context full report in full, the operator's standing instructions quoted, such as a LAND request, and the next step.
   - stop the lanes and their watches. Tell the operator in one line to start a fresh session that continues the epic from that issue. The fresh session re-dispatches each open ticket's brief with BRANCH set to its pushed branch, its report under CONTEXT, and REPORT TO set to its own name for lanes run as separate sessions.

**Reply:** one row per ticket with its PR as a full URL, its verdict and whether it landed, the graph as it ended, the epic verifier's verdict, and what is left for the operator, in the order and form of SKILL.md "Writing the reply".
