### Epic

**You own the ticket graph and the epic's verdict.** Lanes own their tickets. You decide what runs, in what order, and when the epic is done.

Several tickets toward one outcome, each ending in its own PR. You dispatch one lane per ticket and steer them. You write no ticket's code. A single ticket is not an epic, so run its own playbook.

1. **Pin the tickets.** The tracker holds the epic and one issue per ticket. When the operator gave you a body of work rather than tickets, cut it into tickets and create the issues yourself. With no tracker, write the tickets to one file outside the repo's tree and paste each ticket in full into its lane brief. Each ticket must stand alone: the outcome, the files it owns, what is out of scope, and acceptance that ends in an end-to-end check. Fill the gaps yourself from the code. Product and preference calls go to the operator through ask, batched into one round. Flag a ticket **needs design** when it introduces a new data shape, crosses a module boundary, or keeps acceptance you could not make concrete. Its lane runs at frontier. Every other lane runs at strong-code, because its ticket arrives specified and its reviewer and verifier still run at frontier.
2. **Draw the graph.** For each ticket, list the files it writes and the tickets it needs. show it as a Mermaid diagram. Tickets that others need, such as a schema change, a migration, shared types or a flag, are the backbone. Two tickets whose write lists overlap get split or chained, per [separate-before-sharing](../principles/separate-before-sharing.md). Record the graph on the epic's issue, or in the tickets file.
3. **Size the lanes.** Every lane runs heavy checks through the box queue, so working lanes beyond its slots sit parked. Count the slots of the queue your lanes lean on most, per [queue-heavy-checks](../principles/queue-heavy-checks.md), and keep no more lanes working at once than that. A lane whose PR is merge-ready and waiting to land is not working. Say the number and why.
4. **Dispatch the ready tickets.** Find the repo's documented command that prepares a fresh worktree once, and put it in every brief's SETUP. A ticket is ready when every ticket it needs has merged. It is also ready when all but one have merged and that one has a merge-ready PR, and then its lane stacks on that PR's branch. A ticket waiting on two unmerged tickets waits for the merges. When ready work waits only on merges, ask the operator once to land those PRs. dispatch one lane per ready ticket, up to the size from step 3, each with a lane brief from roles.md. track each ticket as its own item, led by its number, and update it from the lanes' reports.
5. **Steer by notices.** Each lane reports back when it is merge-ready, its head moved, it is blocked or it failed. wait for those reports and never poll. When one arrives:
   - **Merge-ready.** Read the reviewer's STATUS and the verifier's verdict on the PR, and the diff's file list and size. A lane saying "ready" is a claim. spawn a reviewer only when the files or the size surprise you. Then dispatch the next ready ticket.
   - **Head moved.** Tell every lane stacked on that branch to rebase onto the new head.
   - **Escalate.** A Failed report, or a Blocked report on a design question from a lane at strong-code, goes one tier up, per roles.md Escalation. have the lane push its branch, stop it, and dispatch the same brief at frontier with BRANCH set to that branch and the failure attached. A failure at frontier comes back to you.
   - **Blocked.** Any other block gets a reply. Settle what you can. Product calls go to the operator through ask. A second block on the same premise means [attack-the-premise](../principles/attack-the-premise.md) before anything else.
   - **A change others build on.** When one lane changes an interface another lane uses, tell that lane what changed and where.
   - **Silent too long.** Read the lane's state, as the binding says, before you message it. stop a lane only to replace it, and say why on its ticket.
6. **Verify the epic.** When every ticket's PR is merge-ready, build the combined result in a scratch worktree, the top of the stack or every branch merged in graph order, yourself or through an editor, and run SETUP there. Then spawn one verifier on that worktree against the epic's own acceptance. One ticket can pass alone while the epic still fails, so this check is never skipped.
7. **Land on request.** Only an explicit request to land, ship or merge starts [shipping](shipping.md), run over the tickets' PRs in graph order. Lanes stacked on a branch that just merged hear from you which base to use now. Each lane owns its own rebase.
8. **Close the lanes.** When a ticket's PR has merged, stop its lane, remove its worktree and tick its item. Update the epic's issue, or the tickets file, with what landed, what did not, and why.

**Reply:** one row per ticket with its PR as a full URL, its verdict and whether it landed, the graph as it ended, the epic verifier's verdict, and what is left for the operator, in the order and form of SKILL.md "Writing the reply".
